## Bug Details

### BUG-002: `/healthz` returns 500 instead of 503 when a session cookie is present 🟡
**Severity**: Medium
**Priority**: P2
**Category**: Functional (operational contract)
**Stories**: 1.0 (health contract, AC 9: 503 when the DB is unusable) × 1.1 (middleware/logging context)
**Affected Features**: `/healthz` under DB failure
**Affected Users**: Operators and monitoring. Only probes or clients that send a `sessionid` cookie (e.g. a browser, or a load balancer with sticky sessions). Cookie-less uptime probes still get the correct 503. No learner-facing impact.
**Workaround**: Configure uptime probes and load-balancer health checks to send no cookies, which is the usual default.

**Root cause (from the 1.1 self-review, consistent with the reproduction)**: with a session cookie, code that runs before the health view evaluates the lazy `request.user`, which loads the session from the DB. When the DB is unusable, that raises `OperationalError` outside the view's own `try`, so Django returns 500. Without a cookie, no session lookup happens and the view's own check returns 503.

**Reproduction**:
1. Fresh DB + one user; `runserver`; sign in through `/ro/accounts/login/` to obtain `sessionid`
2. `chmod -w <data dir>`
3. `curl -i localhost:8770/healthz` → **503** `{"status": "unavailable", "db": "error"}` ✅
4. `curl -i -b "sessionid=<value>" localhost:8770/healthz` → **500** HTML (`<title>OperationalError at /healthz</title>` in DEBUG) ❌
5. `chmod u+w <data dir>`

**Evidence** (QA run, 2026-10-21):
```
GET /healthz  no cookie    -> 503
{"status": "unavailable", "db": "error"}
GET /healthz  with session -> 500  content-type:text/html; charset=utf-8
<title>OperationalError at /healthz</title>
{"level": "ERROR", "logger": "django.request", "event": "Internal Server Error: /healthz", "request_id": "04795b68…", "status_code": 500, "exc_info": "Traceback …"}
```

**Dependencies**: Same endpoint as BUG-001; fix both together. Any middleware or logging filter that touches `request.user` is involved (Story 1.1's request context).
**Recommendation**: Fix later (non-blocking), in the next remediation. Make request-context code avoid **forcing** the lazy user, e.g. read `request.user` only if Django has already resolved it (`_cached_user`), and/or treat a `DatabaseError` while resolving the user as anonymous. Add an integration test that sends a session cookie with the DB unusable and expects 503.
**Assigned To**: DEV
**Target**: CYCLE-1 (before Story 1.10's E2E journeys and DevOps monitoring setup)

**Resolution** (2026-10-21, DEV):
- Fix: `RequestIdMiddleware.process_view` resolves the lazy user inside `try/except DatabaseError`; on failure it keeps the anonymous log context and lets the view decide (→ `/healthz` 503)
- Commit / change ref: `src/infrastructure/web/common/middleware.py:64-79`
- Test evidence: `tests/integration/web/test_healthz.py:50` `test_healthz_returns_503_not_500_when_session_cookie_present_and_db_down` (signed-in client, every DB cursor raising; failed before the fix with `DatabaseError: database is locked`, passes after). Real server: `with session 503`, 0 `Internal Server Error: /healthz` lines
- Status: ✅ Resolved

### BUG-003: CSRF failures show Django's default page, not the localized 403 page 🟡
**Severity**: Medium
**Priority**: P2
**Category**: UI / Functional (spec mismatch)
**Stories**: 1.2 (system-response table: POST without CSRF → "403 page (Story 1.1 handler)") × 1.1 (`handler403`, localized error pages)
**Affected Features**: any form POST whose CSRF token is missing or expired: sign-in, sign-out, and later every content and test form
**Affected Users**: Everyone, most likely a child whose sign-in page stayed open long enough for the token or cookie to expire. They'd see a bare English "403 Forbidden" page with no navigation, instead of the styled, Romanian/English "Access denied" page.
**Workaround**: Reload the page and resubmit.

**Root cause**: Django routes CSRF failures to `settings.CSRF_FAILURE_VIEW` (default `django.views.csrf.csrf_failure`), not to `handler403`. No `CSRF_FAILURE_VIEW` is configured.

**Reproduction**:
1. `runserver`
2. `curl -i -d "username=ana&password=x" localhost:8770/ro/accounts/login/` (no CSRF cookie/token)
3. → **403** with `<title>403 Forbidden</title>` (Django default) ❌; expected: Story 1.1's page (`<title>Access denied</title>`), localized

**Evidence** (QA run, 2026-10-21):
```
POST /ro/accounts/login/ no token -> 403
<title>403 Forbidden</title>
-- 1.1's handler403 rendered directly for comparison:
403 ['<title>Access denied</title>']
```

**Dependencies**: Story 1.4 (localization of the page in `/en/…` requires `LocaleMiddleware`). The fix itself doesn't depend on 1.4.
**Recommendation**: Fix later (non-blocking), in the next remediation. Add `CSRF_FAILURE_VIEW = "infrastructure.web.common.errors.csrf_failure"`, a view with Django's `(request, reason="")` signature that renders the same 403 template (no `reason` text shown to users; log it at WARNING). Add an integration test with `Client(enforce_csrf_checks=True)`.
**Assigned To**: DEV
**Target**: CYCLE-1

**Resolution** (2026-10-21, DEV):
- Fix: `CSRF_FAILURE_VIEW = "infrastructure.web.common.errors.csrf_failure"`; the new view renders Story 1.1's 403 page (or the HTMX partial) and logs `csrf.failure` at WARNING with Django's `reason`, which is never shown to the user
- Commit / change ref: `src/config/settings/base.py:160-161`, `src/infrastructure/web/common/errors.py:58-65`
- Test evidence: `tests/integration/web/common/test_csrf_failure.py` (3 tests: setting wired; full page `errors/403.html` with "Access denied", no Django text, reason logged not shown; HTMX → `errors/_partial.html`), all failed before the fix. Real server: `<title>Access denied</title>`, `"event": "csrf.failure" … "reason": "CSRF cookie not set."`
- Also fixed (found while verifying): a **test-isolation leak**. Story 1.2's tests left `en` active on the thread, so later `/ro/…` requests 404'd without `LocaleMiddleware`. Added the autouse fixture `_reset_active_language` in `tests/conftest.py:72-81`.
- Status: ✅ Resolved

## Deviations from Report Suggestions

- BUG-002: the triage suggested checking `_cached_user`. A narrower `try/except DatabaseError` around user resolution was used instead, so the log context keeps working normally and only the failure case degrades to anonymous.
- BUG-003: a draft assertion expected the request id on the 403 page. Story 1.1 shows the reference only on 500 pages by design, so the assertion was removed (test error, not a product change).
- Extra fix: the language-leak isolation bug in the test suite (see BUG-003 resolution).

## Lessons Learned

1. "Passes alone, fails in the suite" pointed to shared thread state (the active language), not to the code under test. A probe test confirmed it before anything was changed.
2. A bug in "which check runs first" can only be tested by reproducing the real failure order. Patching the check (`os.access`) hid BUG-001.
